# @cs/demo — working notes
Demo-data seeding for `cs_demo` (screen coverage, sign-in links) and the `db:snapshot`/`db:restore` tooling.

## Gotchas
- **`cs_demo`** lives on the same Neon server and roles as `cs_dev`; `pnpm demo:reset` creates it (if Neon refuses `CREATE DATABASE`, create `cs_demo` in the Neon console and re-run).
- **A demo reset invalidates old sign-in links:** every demo contact gets a new id. Use fresh ones (`pnpm demo:links`, or the dev panel after the reset finishes).
- **A new screen registers in the seed's coverage test:** add seed data (`src/<area>.ts` called from `seed.ts`) and an entry in `src/coverage.ts`; `coverage.test.ts` fails for an unlisted screen or an empty listed tool. Then `pnpm --filter @cs/demo coverage:readme` refreshes the README table. The coverage test seeds ~400 reviews and 2,000 rank snapshots on Neon and takes several minutes.
- **Topic-proposal limit:** `topic_proposal_pending_unique` allows one `proposed` row per vertical, so the demo has 2 pending proposals (not the spec's 3) plus one approved and one rejected; Lakeside Family Dental is seeded as a dental prospect to make the second possible.
- **Snapshot/restore order is load-bearing:** `restoreSnapshot` runs every check (folder and manifest, typed name, client tool versions, target not `_test`) before anything destructive, and takes the fresh snapshot before moving evidence aside or wiping — keep the ordering tests green.
- **PG tools:** `db:snapshot`/`db:restore` refuse PostgreSQL 17 client tools (Neon runs 18): set `PG_BIN` to a folder of PG 18 `pg_dump`/`pg_restore` (owner's: `D:\Program Files\PostgreSQL\18\bin`; it's in turbo's `globalPassThroughEnv`). The round-trip test is skipped without `PG_BIN`.
- **Stop the worker and web app before `db:restore` over `cs_dev`:** `DROP SCHEMA` can block on their connections, and concurrent writes make the row-count check report differences. Manifest row counts are read outside `pg_dump`'s snapshot, so a snapshot taken while the worker writes can show small count differences that are not data loss.
- **Restore failure messages:** before the wipe (or create) it says nothing was changed and names the fresh snapshot and whether evidence was moved aside; after, it names the snapshot and the moved-aside evidence. A create-path restore moves a non-empty evidence directory aside instead of unzipping over it. `db:snapshot` warns (doesn't fail) when the evidence directory is missing or `R2_*` is set (DEV evidence may then be in R2, which is not zipped).
- Git-ignored: `backups/` (snapshots), `.evidence*/` (including `apps/worker/.evidence-demo`).
- **Client billing (9b) ids come from `@cs/billing`'s `demo-connect.ts`** (`DEMO_CONNECT_*`, `demoConnectIds`): the seed writes them to `agency_connect`/`client_billing`, and `gatewayFor(…, 'demo')` registers the same accounts, products, prices and subscriptions in its in-memory fake (`seedDemoConnect`), so demo actions (turn billing on/off, change price, Manage payment) work. Change a demo Stripe id or amount only in that fixture. The fake is per process and in memory: what demo actions do to it (a cancelled-at-period-end flag, a moved price) is lost on a web restart while the DB keeps it; `pnpm demo:reset` realigns both.
- **Rehearsal: run `seed`, `fault` and `approve` with the same DB URL form (host)** — `guardManifestRun` compares `<host>/<db>` strictly, so pooler-vs-direct is refused (message gives no hint). Operating steps: `docs/OPS.md` § Rehearsal; never run it against prod or `cs_dev`.
- **Rehearsal CLI (7c2, `pnpm --filter @cs/demo rehearsal <seed|fault|approve|report|teardown|latency>`, code in `src/rehearsal/`) is for the staging rehearsal only.** Every writing command runs `guardRehearsalWrite` first: refuses a `_test` database, any agency not named `Rehearsal …`, and (seed/teardown) a `--confirm-db` other than the URL's `<host>/<db>`. Tests call the command functions directly with `allowTestDatabase` (the CLI never sets it). `fault`/`approve` have no `--confirm-db`: they need the manifest and `guardManifestRun` (service URL = `manifest.database`; approve's `APP_DATABASE_URL` the same host/db; fault also needs a live `Rehearsal Agency NN` and the manifest's delivery Monday). Seed runs in one transaction (fixed auth user ids `rehearsal-NN-admin/am`, so a re-seed needs a fresh staging branch) and only Monday–Thursday before 22:00 Chicago. Seed writes `rehearsal-manifest.json` (repo root, gitignored; ids, live slice, seed time, delivery Monday) that approve/report read; competitors use `fixturePlaceId(name)` + a pinned `googleAdvertiserIds` (domain-mode fixture ads are filtered out), pages `https://fx<1-5>.rehearsal.rivalmonday.app/g<client#>/s<1-3>/…` named like the fixture site. No evidence is seeded (past briefs are `quiet`, item-less). `approve` goes through `createToolRegistry(...).invoke(admin, 'approve_brief')` (audited). `fault` must run before Thursday 22:00 local. `report` (owner URL; weekly lines = weekly clients only, starting-point clients only on their own line) reads `pgboss.job ∪ archive` and the fixture-host log; the "Crawl-delay host does not slow the others" line compares p95 re-capture lag of fx1–fx4 pages that came due while fx5 was busy vs idle (a proxy). `teardown` only writes `rehearsal-archive.sh` (`@cs/demo` can't import the worker). `latency` (cs_dev) skips `provider = 'rehearsal'` rows and keeps tasks with < 5 samples.
