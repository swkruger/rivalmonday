## 1. What we are building

**Rival Monday** (internal codename *CompetitorSpy*; repo `swkruger/rivalmonday`) is an agency-owned, white-labelable SaaS that monitors the competitors of **local-service small businesses** (pilot verticals: HVAC/plumbing and dental) using **public information only**. It turns raw changes (competitor websites, Google Business Profile, reviews, Google/Meta ads, hiring, local rankings) into:

- a **full dashboard** for agencies and their clients,
- a **remote MCP server** so every data point is queryable from Claude/ChatGPT,
- an in-app **Ask assistant** ("Friday") that answers questions and recommends next steps,
- a weekly **evidence-backed brief** (every sentence links to a stored snapshot — *no evidence, no claim*) plus instant alerts.

Business model: first sold to the owning agency's own clients, then **wholesale white-label to other local-service agencies** (feasibility study verdict: conditional go; direct-to-SMB parked).

## 2. Decisions made with the user (do not re-litigate)

**Product & business**
- Agency-owned product; local-service SMB clients; channel = own clients first → wholesale white-label to agencies (Phase 2 of the business, ~months 6–9).
- **Full-stack MVP**: dashboard (agency + client), MCP server, Ask assistant, briefs — not an email-only product.
- Pilot verticals: HVAC/plumbing and dental. US-first.

**Brand (Phase 0, done)**
- Product name **Rival Monday**; wordmark `rivalmonday` (one word, lowercase) — `rival` in **#2A6BAC**, `monday` in accent **#F5A524**.
- Default AI assistant **Friday** (agencies can rename), shown as an orange pill badge (#F5A524 bg, #3B2300 text).
- Direction "A2 · sky blue leads": primary **#47A8E7**, secondary **#2A6BAC**, accent **#F5A524**, ink #0B2540, canvas #F6F9FC, **dark text on grey** panels (#EEF2F6). **White text on #47A8E7 is accepted** by the owner despite 2.6:1 contrast (recorded decision).
- Inter typeface. Content centred with **max-width 1560px** on wide screens.
- UI inspiration: Paige by Merchynt (card KPIs, highlighted CTA panel, per-tier *Manual / AI approval required / AI fully automated* switches, white-label settings page).
- Pending: register rivalmonday.com + .ai; trademark attorney knockout search (watch monday.com marks).

**Stack & infrastructure**
- TypeScript monorepo (pnpm 10 + Turborepo), **Node 24** locally.
- Frontend (Phase 5): **React + Next.js App Router + Tailwind CSS + shadcn/ui**, brand tokens as CSS variables overridden per agency.
- **Vercel** for web/API/MCP/cron (hybrid): one always-on **worker container** (Railway/Fly) for pg-boss jobs + Playwright crawling.
- **Neon Postgres** (dev + tests; project has DBs `cs_dev` and `cs_test`); Postgres RLS for tenant isolation.
- Evidence storage: Cloudflare **R2** (filesystem store for local dev).
- Models: **OpenRouter** for generative tasks (config in `packages/ai/config/ai.yaml`); **Jev (TypeSafe System One)** for typed decisions behind a `DecisionProvider` with confidence cascade Jev → LLM → human review.
- Auth (Phase 5): Better Auth (magic link, Google, orgs, OAuth 2.1 provider for MCP).

**Process preference:** the user chose **subagent-driven development** (fresh implementer per task + reviewer per task + final whole-branch review) and wants plans in **phases with small tasks**.

## 6. Hard-won gotchas (read before writing code)

- **Drizzle `sql` + JS arrays:** a bare array inside `sql\`...\`` expands to a parameter *list*, not an array. Build arrays with ``sql`ARRAY[${sql.join(items.map((x) => sql`${x}`), sql`, `)}]::uuid[]` ``.
- **Drizzle 0.44 wraps driver errors** (`DrizzleQueryError`); the Postgres message is on `err.cause.message` — use `errorText()` from `@cs/db/test-helpers`.
- **drizzle-kit may order a composite FK before the unique constraint it needs** — reorder generated SQL by hand when tests fail on migrate (happened in `0002`).
- **Never edit applied migrations** (`cs_dev` is now at `0030`); add new ones. Custom SQL via `pnpm --filter @cs/db generate --custom --name=<x>` with `--> statement-breakpoint` separators.
- **RLS patterns:** tenant tables use `agency_id = app_agency_id() AND app_client_visible(client_id)`; global public-data tables use `app_competitor_visible(competitor_id)` (Phase 2a) and are **written only by the service role** (REVOKE INSERT/UPDATE/DELETE from `app_user`). Revoking changes error text from "row-level security" to "permission denied" — update tests accordingly. The guard test fails if a new public table lacks forced RLS.
- **Turborepo strict env mode:** env vars reach tasks only if listed in `turbo.json` `globalPassThroughEnv` (already: `TEST_*`, `DATABASE_URL`, `TYPESAFE_API_KEY`, `OPENROUTER_API_KEY`, the DataForSEO/Apify/ScrapeCreators keys, `REVIEWER_HASH_SALT` and `ANTHROPIC_API_KEY`).
- **`.env` loading:** each package's `vitest.config.ts` / entry point calls `process.loadEnvFile(<repo-root>/.env)` in try/catch — count directory levels carefully (a wrong depth silently loads nothing; it bit us once).
- **Git Bash on Windows:** don't `source .env` (values contain `&`); parse with `grep '^KEY=' .env | cut -d= -f2-`. `timeout` + pnpm exits 143 on SIGTERM — cosmetic.
- **pg-boss 10:** queue names with hyphens; `work()` handlers receive arrays; worker uses the owner `DATABASE_URL` for now (least-privilege role is a Phase 7 item).
- **Jev API:** `POST https://api.typesafe.ai/v1/systemone`, model `jev-latest` (returns `jev-1.13.0`); noul has no confidence field (derived); score = average, level = argmax.
- **Crawler conduct is non-negotiable:** honest UA `RivalMondayBot`, RFC 9309 robots (5xx/unreachable ⇒ disallow), ≥3 s per host, blocked ⇒ record, never evade.
- **Worker = one replica.** Per-host rate limiting is in-process; don't run `collect-once --poll` (or a web crawl of the same domain) while the worker runs.
- **app_user privileges:** the privilege guard test enumerates every public table and asserts an exact allow-list (`client`, `client_competitor`, `competitor_suggestion` UPDATE(status) only). A new tenant table that app_user writes must be added there. **Since Phase 3d, `client` UPDATE is column-granted, not table-wide:** `app_user` can `UPDATE` only `name, vertical_id, features, services, keywords, service_area, place_id, score_thresholds` — `self_competitor_id` and `agency_id` are service-role only; Phase 4a added `timezone` to the grant (table-wide UPDATE was revoked and re-granted column by column; Postgres has no column-level REVOKE finer than the table grant it's carved from, so a future editable column needs a new `GRANT UPDATE (col) ON client TO app_user`, not a broader table grant).
- **Vendor quirks (live-verified):** DataForSEO can answer 200 with an OK envelope but a task-level error (check `isDfsOk` per task); `task_get` repeats the cost but isn't billed (ledgered at $0); `data.tag` echoes our competitor id (tasks are mapped by tag); Apify returns an error *item* for pages with no ads; `ads_search` by domain returns other advertisers' creatives (filtered by name); owner replies greet reviewers by first name (redacted).
- **Commit trailer** on every commit: `Co-Authored-By: Claude Opus 5.5 (1M context) <noreply@anthropic.com>` (subagent-authored commits may name their own model, e.g. Sonnet 5 — accepted). Never stage `.env`, `.claude/`, `App/`, `.superpowers/`.
- **Engine needs `OPENROUTER_API_KEY`** (embeddings + LLM fallback); without it `engine-sweep` skips and captures don't enqueue diffs. `TYPESAFE_API_KEY` is optional (decisions fall back to the LLM).
- **Engine retries:** a failed stage is re-offered by the 5-minute `engine-sweep` only after 30 × 2^(attempts−1) minutes; after 5 attempts (~7.5 h) it is exhausted and logs `[engine] stage … exhausted`. To re-run an exhausted subject, delete its `stage_run` row (service role) or bump the stage version.
- **Running the full test suite:** it takes ~18–20 minutes against Neon — longer than the Bash tool's 10-minute cap, so run it with `run_in_background` and wait for the completion notice, starting no other test run meanwhile. Two concurrent runs collide on the shared `cs_test` database (FK/duplicate-key errors, TRUNCATE deadlocks). Neon is sometimes slow enough that DB tests approach vitest's 30 s default timeout — re-run the failing package once before suspecting the code.
- **Subagent implementers and tests (learned in Phase 3d):** tell implementers to run *focused* tests in the foreground (`timeout: 600000`) and to poll any background whole-package run themselves with short foreground checks. Several implementers handed back mid-run or waited on a wake-up that never came, leaving work uncommitted; the dispatch must say "never hand back while a test run you started is still running".
- **Focused test runs:** `pnpm --filter <pkg> exec vitest run <pattern>`. `pnpm --filter <pkg> test -- <pattern>` does *not* narrow — it runs the whole package suite.
- **Line endings:** the repo is LF-only (`.gitattributes` `* text=auto eol=lf`, added 2026-10-02 after a subagent rewrote 21 files as CRLF). Write files with LF; `git ls-files --eol | grep crlf` should print nothing.
- **Captures and evidence are immutable at the DB level** (triggers block UPDATE/DELETE for every role; only `capture.legal_hold` may change). Competitors/tracked pages with captures can't be deleted (FK RESTRICT). Retention deletion is a Phase 7 feature.
- **Naming (Phase 3a):** `EMBEDDING_DIMENSIONS` (`@cs/db`, = 512) is the single source of truth for embedding width — matches `vector(512)` columns and `dimensions: 512` in `ai.yaml`'s `embeddings` task. The engine's output row is `changeEvent` (table) / `ScoreFactors` (stored on `event_score`) — not "eventChange".
- **Money changes are never masked:** per spec §6.1, any detected price/percent change always forces a web diff to be flagged and a tag result to be `meaningful`, regardless of volatile-block masking, model confidence, or what the LLM/Jev decision actually answered — see `gateChange` in `packages/engine/src/web/diff-stage.ts` and the `forced`/`money` logic in `resolveTag` (`packages/engine/src/tag/questions.ts`). Date- or duration-only changes are still detected but can be dismissed as cosmetic by the model; a low-confidence dismissal also writes a `decision_review` row.
- **Vendor captures diff only after a 10-minute settle delay (Phase 3b):** collectors write ad/review/job/GBP rows *after* the `capture` row, so a structured diff run too soon would see nothing — the stage refuses to claim a capture younger than that, and the sweep simply skips it until next time. A capture posted this minute will not have a structured diff for at least 10 minutes.
- **Rank changes/events are tenant-private (Phase 3b):** `rank_change` is the one `ChangeType` that is never global — rank scans come from one client's tracked keywords, so `detected_change`/`event` rows for it always carry `agency_id` **and** `client_id` (CHECK-constraint enforced), are scored only for that client, are hidden from every other tenant by RLS, and are never cross-channel merged with another event.
- **Engine queues use the `short` pg-boss policy with a per-subject `singletonKey` (Phase 3b):** at most one *queued* job per subject (capture/change/event/client) — a subject still queued from the previous sweep is not enqueued again. This closed the Phase 3a "sweep re-enqueues have no dedupe" carry-over.
- **`competitor.meta_page_id` is gone (Phase 3b, migration `0021`):** use `competitor.meta_page_ids` (plural, up to several Meta pages per franchise competitor) — the old singular column and any code reading it will not compile/run.
- **`redactForModel` (Phase 3c), not bare `redactContactInfo`, at every model boundary:** every text placed in a decision state, chat message or embedding input must go through `redactForModel` (`@cs/collectors`) with the business's own name(s) passed as `businessNames` where known — it adds `compromise` NER person-name redaction and a serious-health-condition list on top of contact-detail redaction. A lone `redactContactInfo` call at a new model-input site is a privacy regression, not a style choice.
- **A review's stage subject is `md5(review_id || '|' || text)::uuid` (Phase 3c):** editing a review's text changes its subject id, so the `review_themes` stage treats it as new work and re-analyses it — but `review_analysis`'s primary key is `(review_id, vertical_id)`, not the stage subject, so the fresh analysis's `onConflictDoUpdate` *replaces* the pre-edit row in place; there is no orphaned row left behind.
- **`competitor` visibility now also covers a client's own self business (Phase 3c):** `app_competitor_visible()` admits a competitor if it is either tracked via `client_competitor` *or* is some visible client's `self_competitor_id` — a self competitor is deliberately never in `client_competitor` (its events are never scored/routed, moves never run on it), so don't expect it in a `client_competitor` join; look it up via `client.self_competitor_id`.
- **Price spans never end on an out-of-order capture (Phase 3c):** `price_extract`'s watermark is the newest capture of the page with a **done** stage run; a capture older than that watermark is a no-op (ends/reopens nothing), and a capture whose priced blocks exceed `PRICE_MAX_BLOCKS` (40) ends no spans that pass either — don't expect `price_point.ended_at` to reflect every capture in real time on a catalogue-sized page.
- **Complaint-spike (`review_spike`) detected changes have `stage_version: 1` and no `stage_run` row (Phase 3c):** they're written directly by the nightly `runReviewInsights` job (idempotent via a 30-day per-theme cooldown check, not the `stage_run` claim mechanism other stages use), so don't look for a `stage_run` row to find or debug one.
- **`cs_dev` had zero `agency`/`client` rows until the Phase 3c session:** a minimal `CS Dev Verification Agency` (`aaf5e009-974b-4ce8-b7ec-b722c5c66b1c`) / `CS Dev Verification Client` (`25f99947-4559-4150-ab5d-dd432540aca0`, vertical `hvac_plumbing`, no `place_id`) now tracks `aireserv.com` (`e9f9cbd3-8834-43a4-a1af-a31224ca43d3`) via `client_competitor` — see §5 item 5 and the roadmap's "Phase 3c carry-over" for what it does and doesn't unlock. **Not yet live-verified:** the self-business benchmark path (needs this client's `place_id` set, or a real client with one) and `price_point`/the pricing tracker (needs a real `web`-source capture of a tracked competitor — banned until `https://rivalmonday.com/bot` exists).
- **Events are soft-retracted, never deleted (Phase 3d):** `event.retracted_at`/`retraction_reason` — every reader written against events since Phase 3d (merge candidates, novelty, scoring, the score sweep, moves, and any new one you add) must filter `retracted_at IS NULL`; an old reader that forgot this would resurface a superseded or AM-rejected event's evidence.
- **`detected_change.status` now also takes `superseded` and `suppressed` (Phase 3d):** `superseded` is a diff-stage output of an older stage version once a newer version re-diffs the same subject (its event loses that evidence link and is retracted once no live evidence remains); `suppressed` is the churn guard's catch-all for non-money changes on a churned page (capped at `CHURN_SUPPRESSED_MAX` = 200, flag `churn`, never tagged). Neither status is ever tagged or scored — don't expect a `decision_review`/`event` row for them.
- **`AI_SHADOW_RATE` costs real money (Phase 3d):** setting it (0–1) overrides every task's configured `shadow_rate` and forces that fraction of calls to also ask the LLM, ledgered as `<escalate_to>:shadow` (in practice `llm_decisions:shadow`) — only set it for a deliberate, budgeted live measurement run (e.g. `AI_SHADOW_RATE=1 pnpm --filter @cs/worker engine-once …`), never left on in normal operation. The shipped default shadow rates are low (0.05 generally, 0.02 for `review_decisions`) specifically to keep this cost small.
- **Shadow mode is not the cascade, failure-wise (Phase 3d):** a sampled (shadow) call asks Jev and the LLM in parallel. If Jev answers below threshold and the shadow LLM call fails, the decision returns Jev's low answer with those keys in `needsReview` — it does **not** throw the way the non-shadow cascade does when its fallback fails (only both providers failing throws). And the LLM call of a shadow sample is ledgered as `llm_decisions:shadow` even when its answers were the ones used (Jev below threshold), so `llm_decisions` ledger rows undercount real fallback use by the sampled fraction — add the two when costing or counting escalations.
- **Decision samples/labels/batches/score failures are service-role only (Phase 3d):** `decision_sample`, `decision_label`, `model_batch`, `score_failure` have forced RLS and no tenant policy at all (not even a restrictive one) — `app_user` sees zero rows and cannot write them. Read/write them only through the worker's service-role connection or the `decisions` CLI (which uses `SERVICE_DATABASE_URL`).

- **Brief statuses (Phase 4a):** `generating → ready → approved` (4b adds `sent`), or `failed`. One `brief` per (client, delivery Monday). A failed brief is retried by the next hourly `briefs-schedule` tick up to `BRIEF_MAX_ATTEMPTS = 3`, then stays `failed`; a `generating` row older than 30 minutes is re-claimable, and the claim's `attempts` value is a fencing token — a superseded run's commit or failure update matches zero rows and stores nothing. `brief-once --force` deletes the client's not-yet-approved brief for that delivery date first.
- **Nothing unverified is ever stored as `ready` (Phase 4a):** a writer failure, an unparseable draft or a verifier outage (Jev *and* LLM failing) fails the attempt; an unsupported sentence is dropped, a failed headline drops the item, and a brief with nothing left is `kind = 'quiet'` ("No significant competitor moves this week."). Don't add a code path that stores model text without `verifyDraft`/`verifyText`. Below-threshold support answers count as unsupported and are never queued to `decision_review`.
- **Deterministic number rules are kind-strict (Phase 4a):** money ↔ money only, plain ↔ plain only, percent within ±1 point of an evidence percent; the period's year is allowed. "69 dollars" (no `$`) is dropped. Word numbers and weekdays are not checked.
- **Featured events are never re-gathered (Phase 4a):** an event that appears in an item of one of the client's non-failed briefs is excluded from every later gather, and a move absorbs its own events — expect a later brief to skip it.
- **Move summaries are context, never evidence (Phase 4a fix wave):** `candidateEvidenceText` (the verifier's evidence, rules and support Noul) holds only live event summaries and change texts; `candidateContextText` adds a move's "Detected pattern" line for the writer only. A move whose supporting events were all retracted is not gathered, the commit refuses an item citing no events, and `approveBrief` drops (system feedback, no recommendation) items whose events were retracted after the brief became ready. Gather windows events on `event_score.scored_at`.
- **The writer and verifier take the period (Phase 4a fix wave):** `writeBrief(…, period)` and `verifyDraft`/`verifyText(…, { year, period })`. The verifier evidence starts with `Brief period: <start> to <end>.` (plus "Every EVIDENCE item below was detected in this period." when every candidate is an event) so "this week" can be judged; its ISO dates become allowed dates and never numbers. Move recommendations use first detection → now as the period. One live recommendation per move (any source; a dismissed brief recommendation doesn't block, a move recommendation never comes back); a move-recommendation title that fails the rules falls back to the playbook title.
- **`client.timezone` is column-granted (Phase 4a):** `app_user` may `UPDATE (timezone)` like the other editable client columns (default `America/Chicago`, IANA; invalid values fall back via `safeTimezone`). Briefs are scheduled in the client's local time.
- **`upsell_tag` must be stripped for client roles (Phase 4a):** it's agency-only (spec §8.5) but RLS can't hide a column by role — `getBrief` strips it; every new read path over `brief_item`/`recommendation` (4b email/PDF, Phase 5 UI, Phase 6 MCP) must strip it too.
- **Brief review writes lock the brief (Phase 4a):** each AM write transaction takes `SELECT … FOR UPDATE` on the brief and re-checks `status = 'ready'`; reorder permutes the active items' existing `ord` values (unique `(brief_id, ord)` DEFERRABLE INITIALLY DEFERRED, migration `0030`), so ords need not be 0-based or contiguous — always sort by `ord`.
- **Prompts escape every untrusted string (Phase 4a):** competitor names (from scraped GBP titles), the rendered playbook line, the client-context block and all evidence text pass `escapeEvidence` inside tagged blocks; system prompts say never to follow instructions in them.
- **OpenRouter JSON-schema tasks need a ZDR endpoint that supports structured outputs (Phase 4a):** `anthropic/claude-sonnet-5` had none on 2026-10-03 (404 "No endpoints found"), nor did `openai/gpt-5-mini`; the writers now use `anthropic/claude-sonnet-4.6` → `anthropic/claude-haiku-4.5`. Fake-AI unit tests can't catch this — probe live before changing a JSON-schema task's model.
- **Every `.tsx` file in `@cs/email` must start with the two-line JSX pragma (Phase 4b):** `/** @jsxRuntime automatic */` then `/** @jsxImportSource react */`, exactly as the first two lines. `tsx` resolves and applies only the single tsconfig nearest its *process* cwd (matched against that one tsconfig's own `include` glob) to every file it transforms — a template reached from `apps/worker`'s cwd falls outside `apps/worker/tsconfig.json`'s `include` and never gets `jsx: "react-jsx"` applied, crashing with `ReferenceError: React is not defined` the moment it's rendered in production (`tsx src/main.ts`). The pragma makes esbuild emit the automatic runtime regardless of which tsconfig (if any) was resolved. `packages/email/src/jsx-pragma.test.ts` walks every `.tsx` under `src/` and fails the suite if one is missing it — don't add a new template file without the two lines.
- **The outbox row is written inside the same transaction as the state change that causes it (Phase 4b):** an alert release, a brief going `sent`, a withdraw — each writes its `notification` row(s) in that transaction, so a rollback never leaves a stray message and a commit never silently drops one. A new delivery-triggering write that forgets this breaks that guarantee.
- **Lock order: `lockClientAlerts` before any alert row lock (Phase 4b):** every alert write path (sweep, release, approve, dismiss, digest, withdraw) takes the per-client advisory lock first, then row-level locks — a new alert code path must follow the same order or risk a deadlock against the sweep/throttle.
- **`in_app` notification rows are inserted already `sent` (Phase 4b):** they *are* the inbox (Phase 5 reads them and sets `read_at`); only `email` and the reserved `sms` channel go through `pending → sending → sent | failed`. Quiet hours defer `email` (and `sms`) only — `in_app` is never deferred, and agency webhooks ignore personal quiet hours entirely.
- **Client-facing payloads never carry `upsell_tag` (Phase 4b, extends the Phase 4a rule):** every brief/alert email, digest, PDF and webhook payload strips it before a client-facing recipient sees it; agency-facing notices may include it.
- **A brief's `summary`/`kind` are recomputed twice, not once (Phase 4b):** once at AM approval (`approveBriefTx`) and again by `deliverBrief` inside its own locked transaction, right before `finalBriefSummary` — because evidence can be retracted between approval and the delivery tick (`dropRetractedItems` runs both times). Don't assume the approved summary is still accurate at send time.
- **Withdrawn alerts free their merged events (Phase 4b):** `withdrawAlerts` deletes every `alert_event` row except the alert's own primary, so an event that had merged into a now-withdrawn alert is picked up fresh by the next sweep instead of being lost with the alert that swallowed it.
- **The dispatcher re-checks liveness immediately before sending, not just at enqueue time (Phase 4b):** `dispatchDue`'s `undeliverableReason` check (contact still active; for `alert`-kind rows, the alert still exists and is not `withdrawn`/`dismissed`, and its primary event is not retracted) runs right before each send and fails a stale row once, permanently, instead of retrying it.
- **PDFs block every network request except the agency's own `https` logo URL (Phase 4b):** Playwright's brief/report PDF render disables JavaScript and blocks all other requests, so a template that adds a second external asset will silently fail to render it, not error.
- **Webhook URLs are re-checked at send, not only at save (Phase 4b):** the same `https`-only, `hooks.slack.com`/`.webhook.office.com`/`.logic.azure.com`/`.environment.api.powerplatform.com` allowlist (no redirects followed) is applied again immediately before every send, in case a saved URL's DNS now resolves somewhere else.
- **`.outbox/` is the dev mailbox (Phase 4b):** whenever `POSTMARK_SERVER_TOKEN` is unset (the default here), every email is a `.json` + `.html` pair under `EMAIL_OUTBOX_DIR` (`apps/worker/.outbox/` when run via `pnpm --filter`) instead of a real send — open the newest `.html` in a browser to see what a client would receive.
- **A `sent` brief/report with `pdf_key IS NULL` is re-enqueued for rendering every tick, for up to 7 days (Phase 4b):** `listBriefsMissingPdf`/`listReportsMissingPdf` (`PDF_CATCHUP_DAYS = 7`) catch a PDF that was never rendered (a worker restart mid-render, an exhausted retry, a direct CLI send) — a deterministically-failing render is therefore retried roughly hourly for a week (parked as acceptable risk; add a failure counter/backoff if it becomes a problem).
